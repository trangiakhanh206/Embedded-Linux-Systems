========================================
1. REAL-TIME IMPLEMENTATION
========================================

Application: Sensor Monitoring System (SMS)
Platform: Ubuntu Host x86_64
Mode: SMS_HOST_SIMULATION

Sensor interval: 500 ms

Implemented features:
- SCHED_FIFO priority 50
- SCHED_OTHER priority 0
- clock_nanosleep with TIMER_ABSTIME
- CLOCK_MONOTONIC timing
- mlockall(MCL_CURRENT | MCL_FUTURE)
- 256 KB worker thread stacks
- In-memory jitter collection
- CSV export after Sensor Thread shutdown

Both scheduling policies were verified
using pthread_getschedparam().

========================================
5. DEADLINE ANALYSIS
========================================

Sensor interval:
500 ms = 500000 us

Maximum measured wake-up latency:

SCHED_OTHER: 953.648 us
SCHED_FIFO : 330.581 us

Neither run recorded wake-up latency
greater than the 500 ms period.

Suggested evaluation threshold:
Wake-up latency <= 1000 us (1 ms)

Both policies satisfied this proposed
threshold in the measured samples.

Note:
Wake-up latency alone is not sufficient
to prove end-to-end deadline compliance.
Execution and processing times would
also need to be measured.


========================================
6. OPTIMIZATION PROPOSALS
========================================

1. Use SCHED_FIFO priority 50 for
   the periodic Sensor Thread where
   real-time privileges are available.

2. Keep clock_nanosleep with
   CLOCK_MONOTONIC and TIMER_ABSTIME
   to avoid accumulated timing drift.

3. Maintain memory locking where
   supported and avoid unnecessary
   memory allocation in the RT path.

4. Avoid synchronous console output
   and file I/O inside Sensor Thread.

5. Add deadline-miss tracking and
   measure end-to-end response time
   in future improvements.


========================================
7. LIMITATIONS
========================================

Measurements were collected on Ubuntu
Host using simulated sensor readings.

They do not directly establish the same
jitter performance on QEMU ARM hardware.

Each scheduling policy was measured
in one 510-second run.

Background system load may differ
between the two runs.

Results demonstrate observed behavior
under these experimental conditions,
not guaranteed worst-case latency.
